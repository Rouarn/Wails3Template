# 目录重构方案（可行性验证 + 迁移计划）

> 状态：只读实测完成，未移动任何仓库文件、未改仓库配置。所有结论来自本机实验副本 `/tmp/refactor-exp/{a,b,c}`。
> 验证环境：macOS 27.2（arm64）、Go 1.27.3、Wails3 CLI v3.1.0、pnpm 12.16.1、Node 24。
> CI 前提：推送/PR 触发的检查流水线已跑通；打包已拆到 tag 触发的 release workflow（现状见 README 的 CI 说明）。

## 一、结论先行

| 问题 | 结论 |
| --- | --- |
| 能不能搬 | **能**。前端工程整体搬进 `packages/frontend` 已在实验副本里跑通 `pnpm build` / `check:fe` / `check:go` / dev server。 |
| 搬到什么程度 | 推荐 **A（保守版）**：只收敛前端，Go 入口 `main.go` 与 `internal/`、`build/` 都留在根。 |
| B（彻底版） | **按原生 Wails 能力不可行**：`go:embed` 不允许 `..`，`apps/desktop/main.go` 无法嵌入 `packages/frontend/dist`（实测报错见 §3.3）。只能靠构建前把 `dist` 复制进 `apps/desktop` 子树（B′），代价高、收益低，不作为推荐方案。 |
| 代价 | A：39 个文件纯重命名 + 10 个配置文件改动 + lockfile 1 行 importer + 文档 92 处 `frontend/` 引用。一个 commit 可完成，本机除 Windows/Linux 打包外全部可验证。 |

## 二、目标结构

### 候选 A：保守版（推荐）

```
wails3-template/
├── build/                  Wails 平台资源与 Taskfile（config.yml、darwin/、windows/、linux/、appicon.*）
├── docs/                   方案、指南、本文件
├── internal/               Go 业务实现（app/ contract/ infra/ platform/ service/）
├── packages/
│   └── frontend/           前端工程（src/、bindings/、scripts/、index.html、vite.config.ts、uno.config.ts）
├── scripts/                仓库级 Node 脚本（wails.mjs、dev.mjs、check-bindings.mjs、check-icons.mjs）
├── .github/workflows/      CI 三平台矩阵
├── main.go                 Go 入口（Wails 约定：根目录 main 包 + 根相对 go:embed）
├── go.mod / go.sum         Go module（模块路径不变）
├── package.json            编排脚本（dev/build/check:fe/check:go）
├── pnpm-workspace.yaml     workspace：packages/*
├── Taskfile.yml            Wails 任务入口（includes build/**）
└── vite.config.ts          仓库级 vp（lint/fmt）配置
```

职责划分：根目录只放「编排与门禁入口」；前端所有工程性内容（依赖、构建、单测脚本、bindings）都在 `packages/frontend`；Go 侧目录结构完全不动。

### 候选 B：彻底版（不可行，仅记录）

```
apps/
└── desktop/                Go 入口 + internal/（原 main.go 与 internal/）
packages/
├── frontend/               前端工程
└── shared/                 可选：跨端共享类型（当前模板没有实际内容）
```

不可行原因与 B′ 变体见 §3.3、§3.4。

## 三、可行性结论表（逐条实测）

### 3.1 `main.go` 能否移出根目录

| 结论 | 可搬，但需要额外参数/配置改动，不是「零成本」 |
| --- | --- |

- Wails3 CLI **没有**入口目录参数：`wails3 build` 在 `main.go` 里只注册了 `flags.Build`；`internal/commands/task_wrapper.go` 的 `buildWithOperations` 最终执行 `task("build")`，即 `wails3 task build`。
- 真正执行编译的是 `build/darwin|windows|linux/Taskfile.yml` 里的 `go build`，**不带包参数**，默认工作目录是仓库根 → 把 `main.go` 移走会直接报 `no Go files`。
- `wails3 task` 支持 `--dir` / `--taskfile`，但 `wails3 build` 不透传；`wails3 task` 本身从子目录运行也能向上找到根 Taskfile（实测：在 `internal/` 下 `wails3 task --list` 列出 7 个任务，EXIT=0）。

实测（实验 B，`main.go` 移到 `apps/desktop/`、`dist` 已 staging）：

```
$ go build -tags production -buildvcs=false -o /tmp/refactor-exp/b-probe ./apps/desktop
B_GO_BUILD_EXIT=0
```

结论：要移 `main.go`，必须同时改 3 个平台 Taskfile（`dir: apps/desktop` 或 `go build ./apps/desktop`）并把 `BIN_DIR`/`-o` 改成 `{{.ROOT_DIR}}/bin/...`，约 6 行；另见 §3.3 的 embed 约束。

### 3.2 `build/` 能否移动或改名

| 结论 | 可搬；无 CLI 硬编码，但需要同步 35 处路径引用，三平台打包需 CI 复验 |
| --- | --- |

- `build/config.yml` **没有**构建资源目录字段；只有 `dev_mode.root_path`（控制 dev 的监听根与命令 cwd，源码 `internal/commands/watcher.go` 使用 `github.com/atterpac/refresh/engine.Config.RootPath`）。
- `wails3` 不写死 `build/`：`dev` 的 `-config` 是 `scripts/dev.mjs` 显式传入；`generate icons` / `tool package` 的路径都来自 Taskfile 参数。
- 实测（实验 C：`build/` → `tooling/build/`，仅改根 Taskfile 的 4 行 includes）：

```
$ wails3 task --list          # LIST_EXIT=0，列出 7 个带描述任务
$ wails3 task common:go:mod:tidy   # TIDY_EXIT=0
```

- 仍需改的引用（grep 计数，不含 docs）：`build/**/*.yml` 内部 25 处、根 `Taskfile.yml` 4 处、`scripts/dev.mjs` 1 处、根 `vite.config.ts` 5 处；`docs/` 75 处。
- 未验证：移动后三平台打包（`darwin:package` / `windows:package` / `linux:package`）。本机可不带签名跑 `wails3 task darwin:package` 验证 darwin 分支；Windows/Linux 只能靠 CI。

### 3.3 `go:embed all:frontend/dist`

| 场景 | 结论 | 证据 |
| --- | --- | --- |
| A：`main.go` 留在根，前端去 `packages/frontend` | **可行**，embed 改为 `all:packages/frontend/dist` | 实验 A `pnpm build` EXIT=0，二进制生成成功 |
| B：`main.go` 去 `apps/desktop` | **不可行**（原生 embed 不能跨目录） | `/tmp/embedtest`：`//go:embed ../../assets` → `pattern ../../assets: invalid pattern syntax`，EXIT=1 |
| B′：构建前把 `dist` 复制到 `apps/desktop/dist` | 可编译 | 复制后 `go build ./apps/desktop` EXIT=0 |

B′ 需要新增：`build:frontend` 末尾复制 dist、`apps/desktop/dist` 加入 `.gitignore`、embed 改 `all:dist`、清理时机与 dev 热更新配合。这些属于模板不该承担的额外机制。

### 3.4 bindings 生成路径

| 结论 | `-d` 可指定输出目录；`-dir` 可指定扫描目录；默认值仍是 `frontend/bindings` |
| --- | --- |

- 源码依据：`internal/flags/bindings.go` → `OutputDirectory default:"frontend/bindings"`，`PackageDirectory name:"dir"`。
- 实测 `-dir apps/desktop -d frontend/bindings` 可正常生成（254 packages / 4 services / 25 methods），输出目录按 `-d` 生效。
- **隐藏坑（实验中真实踩到）**：`scripts/check-bindings.mjs` 自己调用 `wails3 generate bindings` 且**不带 `-d`**，搬移后它会往 `frontend/bindings` 生成，导致漂移误报：

```
[bindings] 生成产物与仓库不一致…
?? packages/frontend/bindings/
ELIFECYCLE  Command failed with exit code 1.
```

  修法：在该脚本的参数里加 `-d packages/frontend/bindings`，并同步 `git status` 的路径与提示文案（实验 A 中改完后 `check:bindings` EXIT=0）。
- 若 Go 包目录也动（B），bindings 的路径段会从 `github.com/rouarn/wails3-template/internal/...` 变成 `.../apps/desktop/internal/...`，前端 4 个 `@bindings/...` import（`bridge/api.ts` 4 条、`bridge/dto.ts` 1 条）全部要改，且 `eventdata.d.ts` 的 import 路径也会变。A 方案不动 Go 目录，因此前端源码 **零改动**（实测 `test:fe` / `typecheck` 通过）。

### 3.5 pnpm workspace

| 结论 | 可行；包名不变，`--filter` 仍匹配；lockfile 必须重新生成 |
| --- | --- |

- `pnpm-workspace.yaml` 的 `packages: [frontend]` → `[packages/*]`。
- `package.json` 的 `pnpm --filter @wails3-template/frontend ...` 按**包名**过滤，与目录无关；实测 `pnpm build:frontend`、`build`、`test:fe` 全部 EXIT=0。
- 首次 `pnpm install` 会直接失败（lockfile 无新 importer）：

```
ERR_PNPM_PACKAGE_MANAGER_NO_IMPORTER
Cannot install with "frozen-lockfile" because pnpm-lock.yaml has no `importers["packages/frontend"]` entry.
```

  执行 `pnpm install --lockfile-only` 后 `pnpm install` 成功；lockfile 实际改动只有 1 行：

```
- frontend:
+ packages/frontend:
```

### 3.6 CI 路径

| 结论 | 仅 1 处需要改 |
| --- | --- |

`.github/workflows/ci.yml` 中 `git diff --exit-code -- frontend/bindings` → `-- packages/frontend/bindings`。其余步骤通过 `pnpm`/`wails3` 间接引用路径，无需改；`actions/setup-node` 未启用 cache，也没有需要改的缓存路径。

### 3.7 `vp` 根配置

| 结论 | 可行；根 `vite.config.ts` 的 6 处 ignore 需要改 |
| --- | --- |

- 根 `vite.config.ts` 只被 `vp lint` / `vp fmt` / `vp check` 读取，与前端包自己的 `vite.config.ts` 无关；命令仍从仓库根执行。
- `ignorePatterns` 里 `frontend/bindings/**`、`frontend/dist/**`、`frontend/src/components.d.ts` × `fmt` / `lint` 两个块，共 6 处。
- 实测（实验 A 改完后）：`pnpm format:check` EXIT=0（45 files）、`pnpm lint` EXIT=0（30 files，0 warning）。

## 五、风险与执行顺序

### 5.1 必须一次提交完成的动作

| 顺序错会怎样 | 证据 |
| --- | --- |
| 先移 `frontend` 不改 `main.go` embed | `go build` 报 `pattern all:frontend/dist: no matching files found`（实验 B 首轮实测） |
| 先移 `frontend` 不改 `check-bindings.mjs` | 生成到旧默认目录，`git status` 出现 `?? packages/frontend/bindings`，漂移检测假红（实验 A 首轮实测 EXIT=1） |
| 先移 `frontend` 不重生成 lockfile | `pnpm install` 报 `ERR_PNPM_PACKAGE_MANAGER_NO_IMPORTER`（实测） |
| 先改 CI 路径再移目录 | CI 上 `git diff --exit-code -- packages/frontend/bindings` 对空路径恒 0，会变成**假绿** |

因此：目录移动 + 全部配置改动 + lockfile 必须同一个 commit。

### 5.2 推荐执行顺序

1. 打快照：`git tag pre-restructure`（本地即可，不推送也可用于回滚）。
2. `git mv frontend packages/frontend`。
3. 按 §4 的 2–12 项改配置（一次改完）。
4. `pnpm install --lockfile-only && pnpm install`（重建 lockfile 与 `node_modules` 链接）。
5. 本地门禁：`pnpm build:frontend && pnpm build && pnpm check`（实验 A 全部 EXIT=0）。
6. 提交推送双远端，等 CI 三平台绿（只有 Windows/Linux 打包无法本机验证）。
7. 改文档 92 处引用，单独 commit（不触发额外风险，CI 只跑 markdown）。
8. 绿后删除 `pre-restructure` tag。

### 5.3 回滚

- 已推送：`git revert <重构 commit>`（保留历史，最安全），然后 `pnpm install` 重装。
- 未推送：`git reset --hard pre-restructure && pnpm install`。
- 回滚后必须重跑 `pnpm check:bindings`——因为 bindings 目录整体搬动过，`git status` 在回滚后应为干净。
