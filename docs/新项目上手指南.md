## 0. 先读这一页

一个新项目从本模板出发，只有四件事：

1. **拿到模板**：克隆、装依赖、确认 Wails3 版本、跑通基线。
2. **去模板化**：改 Go module、产品名、可执行名、bundle id、图标、窗口标题、配置目录。
3. **清理示例**：删掉系统能力页、设置页中不需要的演示代码，并同步删路由、侧栏、图标、locale、bindings。
4. **开始写业务**：按「Go DTO → Go service → 生成 bindings → 前端 bridge → 页面」的固定链路加功能。

先分清 6 个很容易混为一谈的名字：

| 概念 | 本模板中的位置 | 示例值 | 选型建议 |
| --- | --- | --- | --- |
| 产品名 | `build/config.yml` 的 `info.productName` | `示例项目` | 可以是中文，给用户看 |
| 可执行名 | `Taskfile.yml` 的 `APP_NAME` | `demoapp` | **必须是 ASCII**，决定 `bin/demoapp`、`.app` 内二进制名、安装包文件名 |
| Go module | `go.mod` 第 1 行 | `example.com/demoapp` | 用自己的域名或组织路径，发布后不要改 |
| bundle id / appId | `build/config.yml` 的 `info.productIdentifier` | `com.example.demoapp` | 反向域名，发布后**绝对不能改** |
| 应用名 / 配置目录名 | `internal/app/app.go` 的 `AppName` | `示例项目` | 决定 `~/Library/Application Support/示例项目`；发布后改会造成配置目录迁移 |
| npm 包名 | `package.json` 与 `frontend/package.json` | `demoapp`、`@demoapp/frontend` | 只影响 workspace 过滤，不进入产物 |

> **重要**：本模板的 `build/config.yml` **没有 `executableName` 字段**。可执行名只由 `Taskfile.yml` 的 `APP_NAME` 控制；`config.yml` 只控制产品展示信息。不要照着其他 Wails 模板去找 `executableName`。

## 阶段 0：拿到模板

### 0.1 克隆与远端

```bash
git clone git@github.com:Rouarn/Wails3Template.git my-app
cd my-app
git remote -v
# origin  -> 阿里云效 Codeup
# github  -> GitHub
```

新项目建议**重新初始化历史**，不要把自己的产品提交推回模板仓库：

```bash
rm -rf .git
git init
git add -A
git commit -m "chore: 从 Wails3Template 初始化"
```

如果你希望保留模板提交历史，则保留 `.git`，但要把两个远端改成自己的仓库：

```bash
git remote remove origin
git remote remove github
git remote add origin git@codeup.aliyun.com:<your-org>/<your-repo>.git
git remote add github git@github.com:<your-account>/<YourRepo>.git
```

模板约定：`origin` 是阿里云效 Codeup，`github` 是 GitHub；两端都走 SSH。

### 0.2 工具链与版本

| 工具 | 要求 | 说明 |
| --- | --- | --- |
| Node.js | `>= 22.18.0` | 见 `package.json` 的 `engines` |
| pnpm | `12.16.1`（`packageManager` 固定） | 用 Corepack 或 `npm i -g pnpm@12` |
| Go | `>= 1.26.0` | 见 `go.mod` |
| Wails3 CLI | **`>= v3.1.0`** | 低于该版本不识别 `-config`、`-port`、`-clean`、`-ts` 等参数 |
| Task | 不需要单独安装 | 本模板的 `wails3 task` 是 Wails 内置任务引擎；本次实测机器上没有 `task` 命令，`wails3 build` 仍正常 |
| macOS | Xcode Command Line Tools | 打 `.app`/`.dmg`、签名、公证需要 |
| Windows | WebView2 Runtime、NSIS | NSIS 只在打安装包时需要 |
| Linux | GTK4、WebKitGTK 6.0 | 只在 Linux 构建/打包时需要 |

安装固定版本的 Wails3：

```bash
go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0
```

模板自带版本门禁，任何入口（`dev` / `build` / `package` / bindings）都会先检查：

```bash
pnpm cli:check
# [cli] wails3 v3.1.0（要求 >= v3.1.0）
```

注意：`wails3 version` 把版本号写到 **stderr**，stdout 为空。本次实测：

```text
stdout_bytes=0  stderr_bytes=7
stderr=[v3.1.0]
```

所以脚本里不能只读 stdout；模板的 `scripts/lib/wails.mjs` 已经同时收集两个通道。

### 0.3 安装依赖

```bash
pnpm install
```

- **没有 `install:cn` 脚本**。本模板的 `.npmrc` 已经指向 `https://registry.npmmirror.com/`，直接 `pnpm install` 即可。
- `pnpm install` 会触发 `prepare` 里的 Husky。建议先 `git init`，否则 Husky 可能提示找不到 `.git`。
- 本次实测（依赖已在 pnpm store 中）耗时约 1.3 秒；冷启动取决于网络和 store。

### 0.4 首次运行验证

开发模式（热更新）：

```bash
pnpm dev
```

只构建当前平台二进制：

```bash
pnpm build
```

macOS 产物在 `bin/<APP_NAME>`；它**不是** `.app` 安装包。需要 `.app` 时：

```bash
pnpm package
# 等价于 wails3 package -> darwin:package -> create:app:bundle
open "bin/<APP_NAME>.app"
```

建议在改名之前先跑一次基线，确认模板本身可用：

```bash
pnpm cli:check
pnpm typecheck
pnpm check:bindings
pnpm build:frontend
pnpm check:icons
go vet ./...
go build ./...
```

## 阶段 1：去模板化（改名）

### 1.0 执行原则

1. **先改 Go module，再生成 bindings**；不要先手工改 `frontend/bindings`。
2. **`APP_NAME` 用 ASCII 可执行名**；中文放在 `config.yml` 的 `productName`。
3. **生成物不要手改**：`build/darwin/Info.plist`、`Info.dev.plist`、`build/windows/info.json`、`build/windows/nsis/wails_tools.nsh`、`build/windows/wails.exe.manifest` 都由 `update build-assets` 生成。
4. **唯一例外**：`build/darwin/zh-Hans.lproj/InfoPlist.strings` **不会**被 `update build-assets` 更新，必须手工改（本次实测踩到）。
5. 每改完一类，立刻跑一次对应门禁，避免多处错误叠在一起。

下面的示例值统一使用：

```text
产品名      示例项目
可执行名    demoapp
Go module   example.com/demoapp
bundle id   com.example.demoapp
公司名      Example
```

### 1.1 Go module 路径

**改哪里：**

| 文件 | 字段/位置 | 示例值 |
| --- | --- | --- |
| `go.mod` | 第 1 行 `module` | `module example.com/demoapp` |
| `main.go` | import | `example.com/demoapp/internal/app` |
| `internal/app/app.go` | import | `example.com/demoapp/internal/{contract,infra,platform,service}` |
| `internal/infra/path.go` | import | `example.com/demoapp/internal/contract` |
| `internal/infra/settings.go` | import | `example.com/demoapp/internal/contract` |
| `internal/service/capabilities.go` | import | `example.com/demoapp/internal/contract`、`internal/infra` |
| `internal/service/settings.go` | import | 同上 |
| `internal/service/system.go` | import | 同上 |
| `internal/service/window.go` | import | 同上 |
| `frontend/src/bridge/api.ts` | 4 个 `@bindings/...` import | `@bindings/example.com/demoapp/internal/service/...` |
| `frontend/src/bridge/dto.ts` | 1 个 `@bindings/...` import | `@bindings/example.com/demoapp/internal/contract/models` |
| `frontend/bindings/**` | 生成产物目录 | 重新生成，不手改 |

本次实测：模板源码中 module 路径共 **21 处 / 11 个文件**（不含 `bin/` 与生成后的 `frontend/bindings`）。

**命令：**

```bash
go mod edit -module=example.com/demoapp

# 只替换 Go 源码里的 import，不要碰 frontend/bindings
grep -rl 'github.com/rouarn/wails3-template' --include='*.go' . \
  | xargs perl -pi -e 's#github\.com/rouarn/wails3-template#example.com/demoapp#g'

# 前端 bridge 的两处 import 也要同步
grep -rl 'github.com/rouarn/wails3-template' frontend/src/bridge \
  | xargs perl -pi -e 's#github\.com/rouarn/wails3-template#example.com/demoapp#g'

go mod tidy
wails3 generate bindings -clean=true -ts -i
pnpm typecheck
```

`-clean=true` 会删掉旧的 `frontend/bindings/github.com/rouarn/...`，本次实测确认旧目录被清除、新目录为 `frontend/bindings/example.com/demoapp/...`。

**漏改的后果（本次实测）**：

```text
src/bridge/api.ts(3,38): error TS2307: Cannot find module
  '@bindings/github.com/rouarn/wails3-template/internal/service/capabilitiesservice'
  or its corresponding type declarations.
```

### 1.2 可执行名：`Taskfile.yml` 的 `APP_NAME`

| 文件 | 字段 | 模板值 | 示例值 |
| --- | --- | --- | --- |
| `Taskfile.yml` | `vars.APP_NAME` | `Wails3Template` | `demoapp` |

```bash
perl -pi -e "s/APP_NAME: 'Wails3Template'/APP_NAME: 'demoapp'/" Taskfile.yml
```

影响范围：

- `bin/demoapp`、`bin/demoapp.app/Contents/MacOS/demoapp`
- macOS 开发包 `bin/demoapp.dev.app`
- Windows NSIS：`bin/demoapp-amd64-installer.exe`、安装后的 `demoapp.exe`
- Linux：`bin/demoapp`、`build/linux/demoapp.desktop`、`nfpm.yaml` 中的路径
- DMG 文件名

不要用中文可执行名：Windows NSIS、macOS codesign、Linux 包名、脚本路径都会变得不可控。产品名可以中文，可执行名保持 ASCII。

### 1.4 生成 macOS / Windows 构建资源

改完 `config.yml` 与 `Taskfile.yml` 后，**从仓库根目录**执行：

```bash
wails3 task common:update:build-assets
```

它会：

- 读取 `build/config.yml` 的 `info`；
- 用 `APP_NAME` 作为二进制名 / 项目名；
- 生成/覆盖 `build/darwin/Info.plist`、`build/darwin/Info.dev.plist`、`build/windows/info.json`、`build/windows/nsis/wails_tools.nsh`、`build/windows/wails.exe.manifest`。

本次实测生成结果：

| 文件 | 关键结果 |
| --- | --- |
| `build/darwin/Info.plist` | `CFBundleExecutable=demoapp`、`CFBundleIdentifier=com.example.demoapp`、`CFBundleName=示例项目`、`CFBundleGetInfoString=示例项目` |
| `build/darwin/Info.dev.plist` | 同上，另有 `NSAppTransportSecurity.NSAllowsLocalNetworking=true` |
| `build/windows/info.json` | 产品名/公司/版本随 `config.yml` 更新 |
| `build/windows/nsis/wails_tools.nsh` | `INFO_PROJECTNAME=demoapp`、`INFO_PRODUCTNAME=示例项目`、`PRODUCT_EXECUTABLE=demoapp.exe` |
| `build/windows/wails.exe.manifest` | `assemblyIdentity name=com.example.demoapp` |

**不要手工运行** `wails3 update build-assets -name 示例项目 -binaryname demoapp`：`-name` 是项目/可执行名，不是产品展示名。本次实测手跑后 `wails_tools.nsh` 的 `INFO_PROJECTNAME` 变成 `示例项目`，Windows 安装出来的 exe 会变成 `示例项目.exe`，与 `bin/demoapp.exe` 不一致。用上面的 `wails3 task ...` 才是正确姿势。

#### `Info.plist` 字段来源

| Key | 来源 | 模板是否已有 |
| --- | --- | --- |
| `CFBundleExecutable` | `APP_NAME` | 有 |
| `CFBundleIdentifier` | `info.productIdentifier` | 有 |
| `CFBundleName` | `info.productName` | 有 |
| `CFBundleDisplayName` | **不生成** | **没有**；需要时手工加，且会被下次生成覆盖 |
| `CFBundleGetInfoString` | `info.description`（本次实测生成结果一致） | 有 |
| `CFBundleShortVersionString` / `CFBundleVersion` | `info.version` | 有 |
| `NSHumanReadableCopyright` | `info.copyright` | 有 |
| `CFBundleIconFile` | 固定 `icons` | 有 |
| `CFBundleIconName` | 固定 `appicon` | 有 |

本次实测中文产品名通过 `CFBundleName` 就能在 macOS 应用选择器 / Dock 名称中正确显示；主窗口标题由 `internal/app/app.go` 的 `Title` 控制，与 `CFBundleName` 无关。`CFBundleDisplayName` 不是必需项。若你确实需要「显示名 ≠ Bundle 名」，在生成后手工加 `CFBundleDisplayName`，并在团队脚本里固定这一步。

#### 本地化字符串（必须手工改）

`update build-assets` **不会更新** `build/darwin/zh-Hans.lproj/InfoPlist.strings`。本次实测改名后、重新打包，`.app` 里的该文件仍然是旧的：

```text
"CFBundleName" = "Wails3Template";
"CFBundleDisplayName" = "Wails3Template";
"CFBundleGetInfoString" = "Wails3Template";
"NSHumanReadableCopyright" = "(c) 2026, Rouarn";
```

需要手工改成：

```text
"CFBundleName" = "示例项目";
"CFBundleDisplayName" = "示例项目";
"CFBundleGetInfoString" = "示例项目";
"NSHumanReadableCopyright" = "(c) 2026, Example";
```

这个文件决定 macOS 原生面板（文件选择、保存、通知授权等）里显示的 App 名称。不改的话，窗口标题是新的，但系统面板仍显示 `Wails3Template`。

校验：

```bash
plutil -lint build/darwin/zh-Hans.lproj/InfoPlist.strings
# build/darwin/zh-Hans.lproj/InfoPlist.strings: OK
```

### 1.5 配置目录名

真实实现：[`internal/platform/paths.go`](../internal/platform/paths.go) 用 `os.UserConfigDir()` 拼 `AppName`：

| 平台 | 实际路径 |
| --- | --- |
| macOS | `~/Library/Application Support/<AppName>` |
| Linux | `$XDG_CONFIG_HOME/<AppName>`（默认 `~/.config/<AppName>`） |
| Windows | `%AppData%\<AppName>` |

本次实测把 `AppName` 设为 `示例项目`，启动后确实创建：

```text
~/Library/Application Support/示例项目/
└── logs/
    └── app.log
```

设置文件是 `settings.json`（首次保存后才出现）。日志是 `app.log`，单文件 5 MB，保留 3 份历史。

建议：

- 产品名可以中文，但如果你不希望用户目录出现中文路径，把 `AppName` 改成 ASCII（如 `demoapp`），`productName` 仍用中文；两者是独立的。
- **发布后不要改 `AppName`**：它同时是单实例标识、日志标识和配置目录。真要改，需要写一次配置目录迁移/备份逻辑。

### 1.7 Linux / Windows 构建资源

**Linux：**

| 文件 | 字段 | 示例值 |
| --- | --- | --- |
| `build/linux/nfpm/nfpm.yaml` | `name` | `demoapp` |

### 3.1 定义 DTO

新建 `internal/contract/note.go`，所有导出结构体放在 `contract`，字段加 `json` tag，并写中文 doc 注释：

```go
package contract

// Note 是便签列表项，前后端共享。
type Note struct {
	ID        string `json:"id"`
	Title     string `json:"title"`
	Content   string `json:"content"`
	UpdatedAt string `json:"updatedAt"`
}
```

### 3.2 实现 service

新建 `internal/service/note.go`：

```go
package service

import (
	"github.com/wailsapp/wails/v3/pkg/application"

	"example.com/demoapp/internal/contract"
)

// NoteService 提供便签的读写能力。
type NoteService struct {
	app *application.App
}

// NewNoteService 构建服务；依赖通过参数注入，不使用全局单例。
func NewNoteService(app *application.App) *NoteService {
	return &NoteService{app: app}
}

// ServiceName 用于 Wails 日志中的服务标识。
func (s *NoteService) ServiceName() string {
	return "NoteService"
}

// List 返回全部便签。
func (s *NoteService) List() ([]contract.Note, error) {
	return []contract.Note{}, nil
}
```

要点：

- 方法必须是**导出方法**，参数/返回值必须是可 JSON 序列化的类型；
- 业务错误用 `contract.NewInvalidArgument(...)` 等构造，返回后由 `MarshalError` 统一转成 `{code,message,details}`；
- 不要在 service 里直接操作前端 DOM/JS；
- 文件、数据库等路径从 `platform.Dirs` 注入，不要写死当前目录。

## 阶段 4：数据与配置

### 4.1 当前真实实现

| 能力 | 文件 | 实现 |
| --- | --- | --- |
| 配置/日志目录 | `internal/platform/paths.go` | `os.UserConfigDir()` + `AppName` |
| 设置持久化 | `internal/infra/settings.go` | `settings.json`，临时文件 + `rename` 原子替换 |
| 设置业务 | `internal/service/settings.go` | 校验 `theme` / `language`，写 `UpdatedAt`，发 `app.status` 事件 |
| 设置模型 | `internal/contract/models.go` | `Settings{theme, language, updatedAt}` |
| 日志 | `internal/infra/log.go` | `slog` 同时写 stdout 与 `app.log`，5 MB × 3 轮转，自动脱敏 `~` 与 `token=` |

关键行为：

- 文件不存在 → 返回默认值；
- JSON 损坏 → 返回默认值（不阻塞启动）；
- 保存 → 先写 `settings.json.tmp`，再 `os.Rename`，避免半截文件；
- 设置路径通过 `SettingsService.FilePath()` 返回给设置页展示。

### 4.2 什么时候该换 SQLite

`settings.json` 只适合**少量、低频、无并发查询**的偏好。出现以下任一情况时换 SQLite：

- 数据量超过几 MB，或列表需要分页/排序/过滤；
- 需要事务（多表写入要么全成功要么全失败）；
- 需要按字段查询、索引、聚合；
- 多个 goroutine 并发读写；
- 需要 schema 演进与版本化迁移。

继续用 JSON 的代价：全量读写、无索引、并发写要靠锁、损坏后只能回退默认值、迁移只能靠代码分支判断。

### 4.3 SQLite 落点与迁移

推荐：

- 数据库放在 `dirs.ConfigDir/data/app.db`，不要放在安装目录、`cwd` 或前端资源目录；
- 用 `database/sql` + 纯 Go 驱动 `modernc.org/sqlite`，避免 CGO 跨平台编译问题；如果团队能接受 CGO，`mattn/go-sqlite3` 也很成熟；
- 打开时执行：

```sql
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
```

- 用 `PRAGMA user_version` 或 `schema_migrations` 表记录版本；
- 迁移前把旧库复制为 `app.db.bak.<version>`，失败时回滚；
- 首次从 `settings.json` 迁移：读取 JSON → 写入 SQLite → 把 JSON 改名为 `settings.json.bak` → 设置迁移标记。

### 4.4 配置该放哪

| 数据 | 建议位置 |
| --- | --- |
| 主题、语言、窗口尺寸 | `settings.json` 或 SQLite 的 `app_settings` 表 |
| 业务数据 | SQLite |
| 缓存/可重建数据 | `ConfigDir/cache`，可随时删除 |
| 日志 | `ConfigDir/logs` |
| 密钥、token、证书 | **不要**放 JSON/SQLite 明文；用 macOS Keychain、Windows DPAPI、Linux libsecret，或由用户显式配置 |

### 5.2 macOS 签名与公证前置

1. Apple Developer Program 账号，申请 **Developer ID Application** 证书。
2. 本机钥匙串安装证书与私钥。
3. `wails3 signing -platform darwin` 按向导配置签名身份与 Apple ID / Team ID。
4. 先 `wails3 task darwin:package` 生成 `.app`，再：

```bash

```

5. 公证后用 `spctl --assess --type execute bin/demoapp.app` 验证。

注意：

- `CFBundleIdentifier` 必须稳定且唯一；
- `CFBundleExecutable` 必须等于 `APP_NAME`，否则会报「executable is missing」（本次实测复现过）；
- 本地化 `.lproj` 必须随包复制，否则原生面板会回退英文/旧名称；
- 公证需要网络与 Apple 服务可用，CI 上要单独配置 secrets。

### 5.3 Windows 签名

```bash
wails3 task windows:sign
wails3 task windows:sign:installer
```

需要 Authenticode 代码签名证书与时间戳服务。先执行 `wails3 signing -platform windows` 按向导配置；CI 上把证书放 secret，避免入库。

### 5.4 Linux 签名

```bash
wails3 task linux:sign:deb
wails3 task linux:sign:rpm
wails3 task linux:sign:packages
```

需要 GPG 密钥；先执行 `wails3 signing -platform linux` 按向导配置。

### 5.5 更新接入点

模板当前**没有**接入自动更新，也没有任何 `app.Updater` / `updater.Init` 占位代码（README 已同步改为「未实现，无接入点」）。Wails v3.1.0 提供 `github.com/wailsapp/wails/v3/pkg/updater`：

- 通过 `app.Updater` 访问，`updater.Init(...)` 初始化一次；
- 能力：`Check` / `DownloadAndInstall` / `CheckAndInstall`；
- 更新源通过 `Provider` 接口接入，官方自带 GitHub、endpoint、appcast、keygen 等 provider；
- 生命周期事件走标准 Wails 事件系统，前缀 `wails:updater:*`（如 `wails:updater:check-started`、`wails:updater:update-available`、`wails:updater:download-progress`）；
- 支持 macOS / Windows / Linux；macOS 对 `.app` 做 bundle 级替换，其他平台替换可执行文件。

建议的落地方式：

1. 新建 `internal/service/update.go`，只暴露「检查/下载/安装/当前版本」四个方法，不要在 UI 里直接调 updater。
2. 在 `internal/app/app.go` 里 `updater.Init(...)` 一次，Provider 指向自己的发布源（HTTPS + 签名/哈希校验）。
3. 前端加「检查更新」页面/按钮，订阅下载进度事件，显示进度与错误。
4. 更新包必须校验签名/哈希；失败要能回滚；区分 stable / beta 渠道。
5. 自更新会替换正在运行的二进制，必须处理「重启后生效」与权限（macOS 签名、Windows 安装目录写权限）。

本次实测未验证更新链路，只确认模板既没有现成实现也没有接入点、`pkg/updater` 在 v3.1.0 中存在，且源码对 macOS 与其他平台都有对应实现（未在 Windows/Linux 实机验证）。

### 5.6 版本号管理

当前版本号出现在：

| 位置 | 用途 |
| --- | --- |
| `build/config.yml` 的 `info.version` | 生成 plist / Windows info.json / NSIS |
| `internal/app/app.go` 的 `AppVersion` | 运行信息页、首页页脚 |
| `package.json` / `frontend/package.json` 的 `version` | npm 元数据 |
| `build/linux/nfpm/nfpm.yaml` 的 `version` | deb/rpm/AUR |

发布前建议按下面顺序改：

```bash
# 1. 改 config.yml 与 app.go、两个 package.json、nfpm.yaml
# 2. 重新生成平台资源
wails3 task common:update:build-assets
# 3. 重新生成安装包
pnpm package
```

理想做法是用 CI 从一个版本源（例如 `build/config.yml` 或 `VERSION` 文件）注入 `AppVersion`（`-ldflags "-X ..."`）并同步 nfpm/package.json，避免 4 处漂移。模板目前是手工同步，发布前务必用 grep 核对。

## 常见坑（含本次实测）

### 坑 1：Wails3 版本低于 v3.1.0，`-config` 不识别

**现象：**

```text
flag provided but not defined: -config
```

低版本还缺 `-port`、`-clean`、`-ts`，生成的 bindings 与本模板的契约不兼容。

**处理：**

```bash
go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0
pnpm cli:check
```

模板的 `scripts/lib/wails.mjs` 已内置版本门禁，不做参数降级。

### 坑 2：`wails3 version` 输出在 stderr（本次实测）

```text
stdout_bytes=0  stderr_bytes=7
stderr=[v3.1.0]
```

只读 stdout 的脚本会解析失败。模板已经同时收集 stdout 与 stderr；自己写 CI 脚本时也要这样。

### 坑 3：`NConfigProvider` 断掉高度链（模板已修复）

Naive UI 的 `n-config-provider` 默认 `height: auto`，会把 `#app → .app-shell` 的 100% 高度链断掉，表现为侧栏只有内容高、主区没有可滚区间。[`frontend/src/styles/main.css`](../frontend/src/styles/main.css#L38-L60) 已显式补：

```css
.n-config-provider { height: 100%; min-height: 0; }
.app-shell { height: 100%; height: 100vh; min-height: 0; }
```

如果你重写布局，不要删这段；新增包裹层时要继续传递 `height: 100%; min-height: 0`。

### 坑 4：图标类名生产漏扫（`check:icons` 的作用）

UnoCSS 只对构建期扫描到的字面量 `i-<collection>-<name>` 生成规则。动态绑定（`:class="item.icon"`、模板字符串、字符串拼接）扫不到，产物 CSS 缺规则，图标盒子还在但图标空白。

模板的 `src/icons.ts` 是唯一图标表，`uno.config.ts` 的 safelist 由它生成；`scripts/check-icons.mjs` 会校验「集合里存在 + dist CSS 里有规则」。

本次实测触发失败：

```text
[icons] 校验失败：
  - frontend/src/views/HomeView.vue:91 图标 i-lucide-not-a-real-icon
    在 @iconify-json/lucide 集合里不存在（集合缺失或图标名拼错）
```

新增图标只改 `src/icons.ts`，不要在两处维护。

### 坑 5：`vue-i18n` 裸 `@` 触发 SyntaxError

locale 文案里出现邮箱、URL 时，裸 `@` 会被当成「链接消息」语法，运行期报 `SyntaxError`。模板已用：

```ts
linkPlaceholder: "https://example.com 或 mailto:someone{'@'}example.com"
```

新增文案时遇到 `@` 一律写成 `{'@'}`。

### 坑 6：macOS 原生面板依赖 `zh-Hans.lproj`，而 `update build-assets` 不更新它（本次实测）

改名后重新生成、重新打包，`.app` 里的 `InfoPlist.strings` 仍是：

```text
"CFBundleName" = "Wails3Template";
"CFBundleDisplayName" = "Wails3Template";
"CFBundleGetInfoString" = "Wails3Template";
"NSHumanReadableCopyright" = "(c) 2026, Rouarn";
```

窗口标题已经变成「示例项目」，但文件选择、保存、通知授权等原生面板仍显示旧名。**必须手工改这 4 个 key**，并用 `plutil -lint` 校验。

### 坑 7：手改 `frontend/bindings` 会被生成覆盖（本次实测）

`wails3 generate bindings -clean=true` 会删除旧目录并重写。手工修 import 或改生成文件，下一次 `pnpm build` / `pnpm check:bindings` 就丢。正确做法：

```bash
# 改 Go service / contract
wails3 generate bindings -clean=true -ts -i
git add frontend/bindings
```

模块路径改名后，旧目录 `frontend/bindings/github.com/rouarn/...` 会被 `-clean` 清掉（本次实测确认）。

### 坑 8：`.npmrc` 的最低发布年龄与「用最新版」冲突

`.npmrc` 的 `minimum-release-age=0` 与 `pnpm-workspace.yaml` 的 `minimumReleaseAge: 0` 是模板为了「当天最新版」刻意关闭的。真实项目改成 `1440` 后，当天发布的版本会被拒绝，`pnpm add @latest` 可能失败或装到较旧版本。两个配置必须同步改，并接受「最新版」不再总是立即可用。

### 坑 9：先跑 `go build ./...` 再构建前端，会因为 `go:embed` 失败（本次实测）

`main.go` 有：

```go
//go:embed all:frontend/dist
var assets embed.FS
```

`frontend/dist` 不存在时：

```text
main.go:15:12: pattern all:frontend/dist: no matching files found
```

正确顺序：

```bash
pnpm build:frontend   # 或 vp build
go build ./...
```

### 坑 10：module 改名后忘了同步 bridge import（本次实测）

```text
src/bridge/api.ts(3,38): error TS2307: Cannot find module
  '@bindings/github.com/rouarn/wails3-template/internal/service/capabilitiesservice'
```

处理：替换 `frontend/src/bridge/api.ts` 与 `dto.ts` 里的 `@bindings/...`，再重新生成 bindings。

### 坑 11：`CFBundleExecutable` 与产物名不一致（本次实测）

把 `.app` 的 `CFBundleExecutable` 改成旧名 `Wails3Template`、但 `Contents/MacOS/` 里只有 `demoapp` 时，`open` 报：

```text
The application cannot be opened because its executable is missing.
```

确保 `APP_NAME`、`build/darwin/Info.plist` 的 `CFBundleExecutable`、`bin/<APP_NAME>.app/Contents/MacOS/<APP_NAME>` 三者一致；改完 `APP_NAME` 必须重新跑 `update build-assets` 与 `package`。

### 坑 12：`wails3 build` 不等于生成 `.app`（本次实测）

`wails3 build` 只产出 `bin/demoapp`（可执行文件）。窗口标题、图标、`Info.plist` 的验证必须针对 `.app`：

```bash
wails3 task darwin:package
open bin/demoapp.app
```

### 坑 13：手工跑 `update build-assets` 时把产品名当成 `-name`（本次实测）

`-name` 是项目/可执行名，`-productname` 才是展示名。模板的 `common:update:build-assets` 用 `APP_NAME` 作为 `-name` 与 `-binaryname`，产品名从 `config.yml` 读。手工跑时如果写：

```bash
wails3 update build-assets -name 示例项目 -binaryname demoapp
```

生成的 `wails_tools.nsh` 会让 Windows 安装成 `示例项目.exe`，与 `bin/demoapp.exe` 不一致。统一用：

```bash
wails3 task common:update:build-assets
```

### 坑 14：Linux desktop 文件与 `nfpm.yaml` 的路径

`nfpm.yaml` 引用 `./build/linux/demoapp.desktop`，该文件由 `linux:generate:dotdesktop` 生成，不要手写。仓库里的 `build/linux/desktop`（无 `.desktop` 后缀）是模板残留，新项目删除。Linux 打包本次未实机验证。

### 坑 15：`build/ios` 残留（本模板已删除）

本模板已删除 `build/ios/**`，README 的「无 ios/android」与仓库现状一致。如果你是从旧提交或旧模板 fork，先删掉 `build/ios` 再改名，否则旧 bundle id 与产品名会污染 grep 检查。

### 坑 16：中文产品名 + 中文配置目录

本次实测中文 `AppName` 可用：路径 `~/Library/Application Support/示例项目` 正常创建，窗口标题正常。但要注意：

- 可执行名仍要用 ASCII；
- 中文路径对 shell 脚本、日志采集、部分第三方工具不友好；
- 发布后再改 `AppName` 会造成配置目录迁移。

折中方案：`productName` 中文，`AppName` 用 ASCII，界面/标题用中文。

## 附录 C：为什么不提供 `bootstrap.mjs`

评估结论：**不做批量改名脚本**。理由：

1. **替换面广且语义不同**：产品名、可执行名、module、bundle id、AppName、npm 包名是 6 个独立概念，不能用一个 `productName` 输入代替；至少需要 5~6 个参数。
2. **生成物与手工文件混在一起**：一部分文件由 `update build-assets` / `generate icons` / `generate bindings` 生成，脚本必须按正确顺序执行，否则会把生成物和手工改动互相覆盖。
3. **容易误伤**：全局替换会命中 `README`、`docs`、`bin/` 产物、旧 bindings、`pnpm-lock.yaml`、生成平台资源（如 `build/windows/nsis/**`）；一旦误伤，排查成本高于手工改。
4. **一次性成本**：每个项目只执行一次，脚本的维护成本高于收益；而改错一个 bundle id 或可执行名的代价很高。
5. **更值得自动化的是「校验」而不是「改名」**：可以加一个只读的 `scripts/check-branding.mjs`，检查旧标识是否为 0、关键字段是否一致、门禁是否通过。这类脚本风险低、可重复使用。

因此本文只提供**逐项命令 + grep 清单 + 生成/校验顺序**。如果团队仍要做脚本，建议：

- 输入至少包含：`productName`、`executableName`、`modulePath`、`bundleId`、`companyName`、`appName`；
- 只改源码白名单文件，不碰 `bin/`、`frontend/bindings`、`pnpm-lock.yaml`；
- 每步之后执行对应生成命令与门禁；
- 先在 `/tmp` 副本上跑通，再允许在真实仓库执行。
